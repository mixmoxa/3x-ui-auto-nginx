Service boundaries make incidents easier to read.

A service boundary describes what the caller can expect and what the owner can reasonably observe.

Editorial team · {{DATE_1}}

In this noteDefine the externally visible contractTrace responsibility through the callWrite down expected failure behaviourRevise the map after real incidents

Define the externally visible contract.

Begin with the request and response, not a diagram of internal modules. Identify which operations are supported, how errors are reported and what data is persistent. A caller does not need to know every worker process to notice that the response code changed. Record whether a timeout is part of the contract or merely an observed default. This distinction makes later investigation less vulnerable to assumptions about implementation details.

Trace responsibility through the call.

When a request crosses a boundary, the downstream service may return an error, take too long or produce a valid response that the caller handles incorrectly. Those cases deserve separate labels. The first failing component is not always the component showing the loudest alarm. Use timestamps and request identifiers if the system already exposes them, but do not add sensitive data to logs simply for convenience. Record the evidence that connects one hop to the next.

Write down expected failure behaviour.

An optional dependency might be allowed to fail while the core operation remains available. A required dependency may need a clear error instead of stale data. Avoid treating every fallback as safe: returning old authorization information or incomplete balances can be worse than refusing the request. The correct response follows the data and the user operation. Describe it before implementing retries so an automated recovery mechanism does not conceal the wrong state.

Revise the map after real incidents.

A boundary map should be small enough for someone to use during an incident. If a failure reveals an undocumented coupling, add the observed relationship and the condition that exposed it. Remove obsolete dependencies when they are no longer part of the service. A diagram that contains every historical detail is difficult to scan. An accurate short map and one concrete incident note are often more useful than a comprehensive drawing that nobody updates.

Further reading

Continue with the journal index, or explore the overview for the wider context. Write down the affected operation, the available evidence and the decision still open. Keep any untested interpretation separate from the observations. This journal describes approaches to engineering review, not a report about a particular customer system or a deployed service.
