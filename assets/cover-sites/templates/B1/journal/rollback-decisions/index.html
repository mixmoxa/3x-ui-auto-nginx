Decide whether to roll back before the release.

Rollback is an operational decision with costs of its own; it should not be treated as a reflex after any warning.

Editorial team · {{DATE_2}}

In this noteIdentify reversible changesChoose a signal that means somethingTreat rollback as another changeClose the loop with a useful record

Identify reversible changes.

A replacement static asset is easy to restore. A schema migration that has already transformed stored data can be much harder to reverse. Before deployment, separate code changes from data changes and list the parts that can safely return to the previous state. A backup provides recovery material, but it does not prove that restoring it is appropriate after new writes have occurred. State which user data must never be discarded by a routine rollback.

Choose a signal that means something.

A release decision should depend on an observable failure: a representative request returns an unexpected status, a required service does not start or an integrity check fails. A single noisy metric without context may not justify reversing a healthy deployment. Decide which signals demand immediate action and which require investigation. Record the baseline before changing the system so the operator can compare the current result with a known condition rather than memory.

Treat rollback as another change.

Reversing code can restart services, interrupt connections and expose compatibility problems with data written by the newer version. Test the rollback path in a disposable environment where possible. Keep precise instructions about the artifact being restored and the expected final process state. If rollback cannot preserve recent user data, stop and escalate the decision instead of silently taking the fastest-looking route. A recovery process must protect the data it is meant to save.

Close the loop with a useful record.

After recovery, distinguish the trigger, the action taken and the evidence that service returned. If no rollback was attempted, say so. Avoid reporting success solely because a deployment command exited with zero status. Check the affected user operation and the relevant data condition. A concise decision record makes the next release safer because it shows which assumptions were confirmed and which need a targeted test.

Further reading

Continue with the journal index, or explore the overview for the wider context. Write down the affected operation, the available evidence and the decision still open. Keep any untested interpretation separate from the observations. This journal describes approaches to engineering review, not a report about a particular customer system or a deployed service.
