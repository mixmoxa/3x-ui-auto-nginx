APPROACH / DESIGN

Clear monitoring follows a useful question.

Define what good service looks like before choosing dashboards or alert thresholds.

01 / DECIDE

Start with the user journey

Identify the important operation: a completed checkout, a successful API request or a delivered message. Name what a user expects and how quickly they expect it. Then define a measurement that can be repeated.

  • Choose a real outcome rather than a proxy metric where possible.
  • Specify the observation window and the population being measured.
  • Keep a written explanation of the calculation for future maintainers.
02 / ORGANISE

Separate symptoms from causes

Symptoms such as an elevated error rate belong in paging decisions. CPU, memory and queue depths often belong in diagnosis. Some infrastructure signals are urgent, but only when they predict a concrete failure mode.

A dashboard with hundreds of unrelated charts can make the first response slower. Keep the initial view small, then follow links to detailed diagnostic data.

03 / RESPOND

An alert is the start of a decision

The alert should contain an actionable consequence, a clear service scope and a starting reference. Document who can act, what can safely be checked and how to tell whether mitigation worked.
