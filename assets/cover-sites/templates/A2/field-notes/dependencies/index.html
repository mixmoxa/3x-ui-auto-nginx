READING / FIELD NOTES

Map dependencies before the incident.

A dependency map is most useful when it shows what a failure changes for a real user, not every possible connection.

Editorial team · {{DATE_3}}

FIELD NOTE / 01

Begin with the user path

Choose one important operation, such as loading an overview page, and trace only the components it needs. Separate required dependencies from optional content. If an image service fails but the document remains readable, that is different from losing the primary response. Record the timeout and fallback behaviour where known. An architecture drawing without failure behaviour often gives a misleading impression of independence.

FIELD NOTE / 02

Follow the direction of failure

A service may depend on a database for reads and an external endpoint for notifications. They need different recovery plans. Ask whether the caller retries automatically, whether those retries multiply traffic and whether a timeout can block a worker. Draw arrows in the direction of requests, then note the response to failure. This helps distinguish the component that first failed from components that merely became overloaded afterward.

FIELD NOTE / 03

Keep ownership specific

A useful map identifies who can inspect the relevant logs and who is allowed to change each component. Ownership does not imply that one person can diagnose everything. Keep credentials out of the diagram; point instead to the approved operational procedure. If a dependency belongs to a different team or provider, describe the observable contract, such as a status code or response deadline, rather than pretending to control its internals.

FIELD NOTE / 04

Test graceful degradation explicitly

Disconnect an optional component in a safe test environment and observe the user-visible result. A good degraded mode may show stale but labelled information; an unsafe mode may silently omit a critical warning. Record what was actually tested and what remains an assumption. Updating the dependency map after an incident should shorten the next investigation, not create a permanent museum of every transient connection.

Further reading

Continue with the field notes index, or explore the overview for the wider context. Compare the advice with a clearly defined measurement on a system you are allowed to inspect. Record the observation window and the affected operation, then describe what the evidence can and cannot establish. A hypothetical example is never a substitute for service data.
