READING / FIELD NOTES

Use error budgets without hiding failures.

An error budget describes tolerated unreliability under a particular objective; it is not permission to ignore broken requests.

Editorial team · {{DATE_2}}

FIELD NOTE / 01

Write the objective in complete terms

Start with the event you count, its denominator and the observation window. For example, the fraction of eligible HTTP requests that receive a successful response over a calendar month is a different objective from availability checked every minute. State how planned maintenance, client errors and retries are treated. The choices affect the result more than the appearance of a percentage. An objective without an event definition is not yet a useful operational rule.

FIELD NOTE / 02

Calculate with matching units

If a service handles ten thousand eligible requests and an objective is 99 percent success, one hundred unsuccessful requests fit within that simple request-based budget. This arithmetic does not say whether the failures were concentrated during a critical workflow. Time-based and request-based objectives require different denominators. Never combine them into one chart by assuming a minute with one request represents the same exposure as a minute with a thousand.

FIELD NOTE / 03

Watch consumption, not a single point

An error rate describes the fraction of failures in a window. A burn rate compares how rapidly the service consumes its allowed budget against the pace implied by the objective. Short windows help detect sudden incidents; longer ones reduce noise and reveal sustained problems. An alert policy should consider both. Without adequate traffic, one failed request can produce an alarming ratio, so include context about sample size.

FIELD NOTE / 04

Use the budget for decisions

When the budget is nearly exhausted, the response should follow the service risks and the source of failures. Pausing a discretionary change may help, but it does not repair an active incident. Review which user journeys failed and whether monitoring counted them correctly. The calculator in the local lab demonstrates the arithmetic, not a live service state. Document assumptions beside the result so a reader cannot mistake an illustrative calculation for measured availability.

Further reading

Continue with the field notes index, or explore the overview for the wider context. Compare the advice with a clearly defined measurement on a system you are allowed to inspect. Record the observation window and the affected operation, then describe what the evidence can and cannot establish. A hypothetical example is never a substitute for service data.
